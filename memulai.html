Memulai ​

Halaman ini membawa kamu dari nol sampai satu work selesai: memasang deuz, menyiapkan proyek, menulis dokumen satu per satu, mengonfirmasi tiap dokumen, mengerjakan task, lalu meng-archive.

Contoh di semua halaman memakai produk fiktif: aplikasi perpustakaan, tempat anggota memesan buku yang sedang dipinjam orang lain.

1. Pasang deuz ​

deuz terdiri dari plugin Claude Code (Markdown dan YAML) dan CLI kecil berbahasa Go yang menjalankan aturan secara pasti. CLI cukup di-build sekali. Go 1.24+ hanya dibutuhkan untuk build; hasilnya satu binary tanpa runtime.

bash
cd /path/ke/deuz
make build        # menghasilkan bin/deuz, dipakai oleh skill

Lalu pasang plugin-nya:

bash
# pasang dari checkout lokal (tersedia di setiap sesi baru)
claude plugin marketplace add /path/ke/deuz
claude plugin install deuz@deuz

# atau hanya untuk satu sesi
claude --plugin-dir /path/ke/deuz

Skill deuz berawalan deuz:, misalnya /deuz:new. Setelah mengubah skill atau aturan di checkout, buka sesi baru agar perubahannya terbaca.

Kalau ingin memakai CLI langsung di terminal, tambahkan bin/ ke PATH atau panggil dengan path lengkapnya. Skill akan mencari CLI di PATH, lalu di bin/ plugin.

2. Siapkan proyek ​

Di repository proyekmu, minta agent:

/deuz:init

Agent membaca README dan struktur repo, lalu menanyakan satu per satu:

  • peran yang ada di tim dan nama lokalnya (analyst, designer, frontend, backend, qa), serta apakah pekerjaan perlu persetujuan bisnis (role business);
  • homes: tempat sumber kebenaran permanen, yaitu spec perilaku (bawaan deuz/specs), file desain, dan definisi API, atau null kalau tidak ada;
  • bahasa isi dokumen (misalnya id).

Hasilnya deuz/config.yaml. Kalau dijalankan langsung lewat CLI, perintahnya seperti ini:

$ deuz init --role analyst=Analyst --role designer=Designer --role frontend=Frontend --role backend=Backend --role qa=QA --role business="Business stakeholders" --home specs=deuz/specs --home design=design --home api=api/openapi.yaml --language id
Created deuz/config.yaml (schema default, roles: analyst, designer, frontend, backend, qa, business).
Next: edit context in deuz/config.yaml, then `deuz new <work>`.

Setelah itu isi context di config.yaml dengan gambaran singkat proyek (stack, struktur folder, konvensi). Agent membaca bagian ini setiap kali menulis dokumen. Pilihan lain dijelaskan di Kustomisasi.

3. Mulai satu work ​

Satu work adalah satu fitur atau satu perubahan. Minta agent:

/deuz:new pemesanan-buku

Agent menanyakan tujuan dan jenis work: feature, enhancement, bug, tech, atau chore. Lalu ia membuat folder deuz/work/pemesanan-buku/ beserta .deuz.yaml, dan menampilkan status awal:

deuz/work/pemesanan-buku  (schema: default)
  ○ proposal        available
  · specs           locked        (waiting for proposal)
  · ui-design       locked        (waiting for specs)
  · api-contract    locked        (waiting for specs, ui-design)
  · tasks-backend   locked        (waiting for specs, api-contract)
  · tasks-frontend  locked        (waiting for specs, ui-design, api-contract)
  · tasks-test      locked        (waiting for specs, ui-design, api-contract)

Hanya proposal yang bisa ditulis. Dokumen lain terkunci sampai dokumen yang dibutuhkannya selesai.

4. Tulis dokumen, konfirmasi, ulangi ​

Polanya selalu sama, untuk setiap dokumen:

  1. Tulis: /deuz:continue (atau /deuz:continue specs untuk dokumen tertentu). Agent mengambil template dan instruksi dokumen itu, membaca dokumen sebelumnya, lalu menulis.
  2. Periksa: baca hasilnya, perbaiki bersama agent sampai benar.
  3. Konfirmasi: pemilik dokumen menjalankan /deuz:ready <dokumen> --as <peran>. Begitu semua pemilik mengonfirmasi, dokumen berikutnya terbuka.

Untuk proposal sebuah feature dengan role business aktif, konfirmasi analyst saja belum cukup:

$ deuz ready proposal --as analyst
proposal confirmed by Analyst; still waiting for Business stakeholders.

Setelah rapat dengan stakeholder, analyst mencatat hasilnya di proposal (bagian Pertanyaan & keputusan dan Persetujuan), lalu mengonfirmasi atas nama bisnis:

$ deuz ready proposal --as business
proposal is ready (confirmed by Analyst, Business stakeholders).
Areas recorded: frontend, backend, api, business
Now available: specs

Lanjutkan dengan pola yang sama: specs (analyst), ui-design (designer), api-contract (backend dan frontend), lalu tasks-backend, tasks-frontend, dan tasks-test yang dikerjakan paralel. Dokumen yang tidak relevan otomatis di-skip. Misalnya, kalau proposal tidak mencentang area design, ui-design di-skip.

Kapan saja kamu bisa melihat posisi work dengan /deuz:status.

5. Kerjakan task ​

Setelah daftar task dikonfirmasi, engineer atau QA meminta agent:

/deuz:apply tasks-backend

Agent mengerjakan task satu per satu dan mencentang (- [x]) task yang sudah terbukti selesai lewat cara verifikasi yang tertulis di task itu. Mencentang task tidak membatalkan konfirmasi daftar task.

6. Archive ​

Setelah semua dokumen ready (atau skipped) dan semua task tercentang:

/deuz:archive

deuz menggabungkan delta spec ke spec permanen di deuz/specs/, menjalankan promote yang tersisa, lalu memindahkan work ke deuz/work/archive/<tanggal>-pemesanan-buku/. Sejak saat itu deuz/specs/ menggambarkan sistem sebagaimana sudah dibangun.

Selanjutnya ​

  • Konsep singkat untuk memahami istilah yang baru saja kamu pakai.
  • Alur kerja untuk jalur yang lebih ringan (bug fix, perubahan teknis).
  • Contoh untuk melihat isi dokumen sungguhan.
