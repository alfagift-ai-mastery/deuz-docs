Keputusan desain ​

deuz dibangun dari ide-ide OpenSpec (versi yang dipelajari: 1.17.0). Tiap entri menjelaskan apa yang dilakukan OpenSpec, apa yang dilakukan deuz sebagai gantinya, dan alasannya. Path yang diawali OpenSpec/ merujuk ke repository OpenSpec.

D1. Artifact punya owner role ​

  • OpenSpec: satu aktor (satu orang dengan agent AI) menulis semua artifact sebuah change, dari proposal sampai tasks. Schema-nya tidak mengenal siapa menulis apa (OpenSpec/schemas/spec-driven/schema.yaml).
  • deuz: setiap artifact mendeklarasikan owners, yaitu daftar role (analyst, designer, frontend, backend, qa).
  • Alasan: di kebanyakan tim produk, pekerjaan ini terbagi ke beberapa role, dan sebagian besar pengerjaan ulang terjadi di titik serah terima: layar dibangun dari spec yang setengah jadi, atau frontend menebak bentuk API. Kepemilikan yang eksplisit membuat serah terima juga eksplisit.

D2. Ready dikonfirmasi, bukan disimpulkan dari keberadaan file ​

  • OpenSpec: sebuah artifact dianggap selesai jika file-nya ada (OpenSpec/src/core/artifact-graph/state.ts).
  • deuz: missing → draft → ready; artifact menjadi ready jika setiap owner role yang aktif mengonfirmasinya (/deuz:ready).
  • Alasan: jika penulis dan pemakai artifact adalah orang yang sama, "file-nya ada" sudah cukup. Jika pemakainya orang lain, file yang ada bisa saja masih setengah jadi; role berikutnya butuh sinyal bahwa ia boleh mulai.

D3. Solo dan tim adalah mode, bukan schema ​

  • OpenSpec: dirancang untuk satu aktor.
  • deuz: schema yang sama melayani keduanya. deuz mencatat role, bukan orang: pengguna solo mengonfirmasi beberapa role sekaligus (--as backend,frontend), sedangkan di tim tiap orang mengonfirmasi satu role.
  • Alasan: cukup satu model yang perlu dipelajari, dan work yang dimulai secara solo bisa diserahkan ke tim tanpa konversi. deuz tidak perlu tahu siapa saja anggota tim.

D4. work/, bukan changes/ ​

  • OpenSpec: pekerjaan yang sedang berjalan disimpan di openspec/changes/<name>/.
  • deuz: deuz/work/<name>/.
  • Alasan: kata "change" terbaca sebagai "mengubah sesuatu yang sudah ada", sehingga membingungkan orang yang memulai fitur yang benar-benar baru. Work adalah unit apa pun dari pekerjaan yang sedang berjalan.

D5. Skip berlaku per artifact, berdasarkan role aktif dan affected area ​

  • OpenSpec: sebuah change bisa melewati specs secara keseluruhan dengan skip_specs: true di .openspec.yaml.
  • deuz: artifact di-skip jika tidak punya owner yang aktif (berlaku untuk seluruh project: tim tidak punya role tersebut) atau jika work tidak menyentuh area-nya (berlaku per work: checklist "Affected areas" di proposal: design, frontend, backend, api). Artifact yang di-skip tetap memenuhi requires.
  • Alasan: komposisi tim berbeda-beda, dan cakupan tiap work juga berbeda. Tim yang hanya backend tidak pernah melihat artifact UI; perubahan logika backend yang tidak mengubah bentuk API men-skip contract. Perubahan kecil tetap ringan tanpa perlu schema "lite" terpisah.

D6. Graph mengikuti dependensi nyata antar-role ​

  • OpenSpec: proposal → specs → design → tasks, dengan specs dan design sama-sama hanya bergantung pada proposal.
  • deuz: proposal → specs → ui-design → api-contract → tasks-backend ∥ tasks-frontend ∥ tasks-test.
  • Alasan: bentuk API mengikuti apa yang perlu ditampilkan dan dilakukan oleh layar, jadi contract datang setelah desain, dan backend maupun frontend harus menyepakatinya. Begitu contract ready, backend, frontend, dan QA bisa menulis kode secara paralel; paralelisme inilah hasil dari menyepakati contract lebih dulu.

D7. Tidak ada dokumen desain teknis terpisah ​

  • OpenSpec: design.md berisi keputusan teknis (konteks, tujuan, keputusan, risiko).
  • deuz: setiap tasks artifact diawali dengan ## Technical decisions.
  • Alasan: di tim yang punya UI/UX designer, "desain" berarti layar; dua artifact yang sama-sama disebut desain menimbulkan kebingungan. Selain itu, artifact terpisah hanya layak menjadi titik serah terima jika dipakai oleh role lain, sedangkan keputusan teknis dipakai oleh role yang menulis tasks itu sendiri.

D8. Tidak ada artifact test-scenarios terpisah ​

  • OpenSpec: tidak ada (test adalah bagian dari tasks).
  • deuz: coverage map milik QA (scenario → test id → suite) menjadi section pertama di tasks-test.
  • Alasan: satu-satunya pemakai daftar scenario adalah task list milik QA sendiri. Scenario di spec sudah menggambarkan perilaku; coverage map menambahkan di mana masing-masing diuji.

D9. API contract berupa Markdown, dimiliki backend dan frontend ​

  • OpenSpec: tidak ada artifact khusus API.
  • deuz: api-contract.md, berisi tabel per endpoint (request, response, error, permission), dimiliki bersama oleh backend dan frontend; backend menerjemahkannya ke definisi API project saat promote.
  • Alasan: contract adalah kesepakatan antara dua role, jadi keduanya menjadi owner. Menulisnya langsung dalam format definisi API (misalnya file OpenAPI) mencampur kesepakatan dengan tooling backend dan kode hasil generate. Menyimpan perilaku di spec dan bentuk di contract mencegah aturan ditulis ulang di dua tempat.

D10. Home, dan home hanya berisi apa yang sudah dibangun ​

  • OpenSpec: satu tempat penyimpanan permanen, openspec/specs/, diperbarui saat archive.
  • deuz: setiap schema menamai sumber kebenaran permanennya (specs, design, api); project memetakannya ke path atau null. Konten masuk ke home bersamaan dengan kode yang mengimplementasikannya: specs saat archive, file desain dan definisi API sebagai task terakhir di task list frontend dan backend.
  • Alasan: file desain dan definisi API biasanya sudah punya home yang diperiksa oleh tool (test kesesuaian visual membandingkan aplikasi dengan desain; code generator meng-compile definisi API). Menaruh desain atau endpoint yang belum dibangun di sana akan merusak pemeriksaan tersebut. Menyimpan salinan permanen kedua di dalam deuz akan menciptakan dua sumber kebenaran yang lama-lama tidak sinkron.

D11. Review tetap di luar deuz ​

  • OpenSpec: review tidak dimodelkan.
  • deuz: juga tidak dimodelkan. Owner mengonfirmasi ready; review terjadi di pull request atau diskusi.
  • Alasan: memodelkan reviewer menambah state dan birokrasi yang sudah ditangani oleh code review. Satu-satunya tempat di mana kesepakatan harus dicatat, yaitu API contract, ditangani lewat co-ownership (D9).

D12. Skill dulu, lalu CLI Go untuk setiap aturan ​

  • OpenSpec: CLI TypeScript (Node 22+) menghitung status dan instruksi; skill memanggilnya. Binary standalone ditambahkan belakangan dengan bun build --compile (OpenSpec/scripts/binary/build.mjs) agar orang tanpa Node bisa memasangnya.
  • deuz: versi pertama hanya berupa skill. Saat uji coba, agent ternyata menerapkan aturan secara tidak konsisten, sehingga setiap langkah berbasis aturan dipindahkan ke CLI yang ditulis dengan Go: satu binary tanpa dependensi per platform, dengan schema yang di-embed lewat go:embed. Skill memanggil CLI dan kembali ke core/RULES.md jika CLI tidak ada.
  • Alasan: hasilnya harus identik di setiap agent (Claude Code, Codex, …) dan setiap role harus bisa menjalankannya, termasuk orang yang tidak akan pernah memasang runtime bahasa pemrograman. Go menghasilkan satu binary kecil secara default dan dikelola oleh engineer backend tim. Menulis konten tetap menjadi tugas agent; hanya aturan yang dipindahkan.

D13. Satu schema default; komposisi tim ada di config ​

  • OpenSpec: schema default dinamai sesuai pendekatannya, spec-driven.
  • deuz: schema bawaan bernama default. Tim mencantumkan role aktifnya di deuz/config.yaml dan boleh meng-override owner sebuah artifact (misalnya tim backend saja yang produknya adalah API: api-contract: [backend, analyst]). Fork dipakai untuk alur yang memang berbeda (role tambahan, artifact yang berbeda).
  • Alasan: menamai schema berdasarkan komposisi tim (full-stack, backend-only) mengikatnya ke stack tertentu dan melipatgandakan jumlah schema. Kebanyakan tim seharusnya tidak perlu menyentuh schema sama sekali.

D14. File produk berbahasa Inggris, bahasa artifact bisa dikonfigurasi ​

  • OpenSpec: bahasa Inggris; konteks project ada di config.
  • deuz: file produk yang dibaca agent atau CLI (template, instruksi, skill, core/RULES.md, core/CLI.md) berbahasa Inggris. language di config menentukan bahasa isi artifact. Keyword normatif dan struktural (SHALL, WHEN, THEN, ## ADDED Requirements, ...) tetap berbahasa Inggris agar bisa di-parse oleh tool. Dokumentasi untuk manusia diatur oleh D22.
  • Alasan: agent dan parser butuh satu bahasa yang stabil, sementara tiap tim tetap menulis dokumennya dalam bahasanya sendiri.

D15. Persetujuan bisnis adalah sebuah role ​

  • OpenSpec: persetujuan tidak dimodelkan; siapa pun yang menulis change memutuskan apakah change itu dilanjutkan.
  • deuz: role business yang opsional menjadi co-owner proposal (gate 1) dan, jika diperlukan, specs (gate 2). Stakeholder tidak menjalankan deuz: analyst mencatat hasil meeting di proposal dan mengonfirmasi --as business.
  • Alasan: banyak tim butuh keputusan bisnis yang tercatat sebelum development dilanjutkan. Co-ownership sudah memodelkan kesepakatan antar-role (D9), jadi gate tidak butuh state baru, dan artifact berikutnya tetap terkunci sampai business mengonfirmasi. D11 tetap berlaku: review isi tetap di luar deuz; yang dicatat hanya keputusannya.

D16. Owner kondisional dari checklist proposal ​

  • OpenSpec: tidak ada owner.
  • deuz: conditional_owners: [{ role, if_area }] menambahkan sebuah role ke artifact jika proposal mencentang area tersebut (business → proposal, business-rules → specs). Owner kondisional milik proposal sendiri mengikuti checklist-nya sebagaimana tertulis; artifact berikutnya mengikuti area yang sudah tercatat.
  • Alasan: perbaikan bug tidak boleh menunggu meeting, sedangkan fitur harus. Satu schema melayani keduanya, diputuskan per work, dan project tanpa role business tidak terpengaruh.

D17. Proposal melayani bisnis dan engineering ​

  • OpenSpec: proposal ditujukan untuk implementer: Why, What Changes, Capabilities, Impact (OpenSpec/schemas/spec-driven/templates/proposal.md).
  • deuz: bagian bisnis lebih dulu (ringkasan, alasan, tujuan dan indikator, scope beserta prioritas, siapa yang terdampak, risiko, aturan yang butuh persetujuan, pertanyaan dan keputusan, persetujuan), lalu jembatan ke engineering (capability, affected area). Aturan bisnis hanya ditunjuk; teksnya ada di specs.
  • Alasan: dokumen yang sama dipresentasikan ke stakeholder dan diserahkan ke tim. Menulis aturan sekali saja, di specs, mencegah ketidaksinkronan antara ringkasan dan salinan detail di dua dokumen.

D18. Jenis work dan triage yang tercatat ​

  • OpenSpec: tidak ada jenis work.
  • deuz: Type (feature, enhancement, bug, tech, chore). Jika role business aktif, feature wajib mencentang business; bug atau enhancement tanpa centang itu wajib mencatat baris Triage:. Artifact specs di-skip jika proposal yang sudah ready tidak mencantumkan capability dan tidak ada delta.
  • Alasan: yang menentukan gate adalah dampak bisnis, bukan label, tetapi melewati gate harus meninggalkan jejak. OpenSpec men-skip specs dengan skip_specs: true di .openspec.yaml; deuz membaca daftar capability yang memang sudah ada di proposal.

D19. Tabel contoh di scenario ​

  • OpenSpec: scenario berupa bullet WHEN/THEN.
  • deuz: sebuah scenario boleh diikuti satu tabel contoh; tiap baris adalah satu test case, dan tabel ikut digabung bersama requirement-nya.
  • Alasan: aturan perhitungan paling jelas, dan paling mudah dicek oleh pembaca bisnis, jika ditulis sebagai input dan hasil yang diharapkan.

D20. Approvals berada di luar hash proposal ​

  • OpenSpec: tidak ada hash konten.
  • deuz: section <!-- deuz:approvals --> tidak ikut dihitung dalam hash proposal; semua section lain, termasuk pertanyaan dan keputusan, ikut dihitung.
  • Alasan: gate 2 dicatat setelah gate 1. Jika approvals ikut di-hash, baris gate 2 akan membatalkan gate 1 dan menandai semua artifact berikutnya.

D21. Manifest work adalah .deuz.yaml ​

  • OpenSpec: .openspec.yaml menyimpan metadata change (schema, created, goal, affected areas, initiative link, skip_specs, retire_capabilities; OpenSpec/src/core/change-metadata/schema.ts:38-61), tetapi tidak menyimpan metadata navigasi; urutan artifact hanya ada di schema.
  • deuz: .deuz.yaml juga memuat title, requirement, dan pola file tiap artifact (format: 1), yang didokumentasikan di docs/manifest.md. deuz status --write menambahkannya ke work yang lebih lama.
  • Alasan: editor dan viewer bisa menampilkan navigasi langkah demi langkah antar-dokumen sebuah work tanpa perlu mengenal schema deuz, dan tanpa frontmatter yang akan mengubah hash konten dan mengotori dokumen yang di-render. Pola file, bukan daftar file, membuat navigasi tetap mutakhir saat ada file yang ditambahkan di antara dua kali CLI dijalankan.

D22. Dokumentasi untuk manusia berbahasa Indonesia ​

  • OpenSpec: dokumentasi berbahasa Inggris.
  • deuz: README.md dan semua isi docs/ berbahasa Indonesia. File yang dibaca agent (schema, template, instruksi, skill, core/RULES.md, core/CLI.md) tetap berbahasa Inggris. Keyword struktural (SHALL, WHEN, THEN, ## ADDED Requirements, ### Requirement:, #### Scenario:, Type, Triage:, <!-- deuz:… -->) tetap berbahasa Inggris di mana pun.
  • Alasan: pembaca pertama adalah tim internal, yang lebih cepat belajar dalam bahasanya sendiri. Agent dan parser butuh satu bahasa yang stabil. Entri ini menggantikan bagian dokumentasi di D14; terjemahan untuk open source bisa menyusul.
