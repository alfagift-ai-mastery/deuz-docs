Tim dan Git ​

deuz tidak menggantikan branch, pull request, atau code review. Ia hanya mencatat satu hal yang tidak dicatat Git: siapa sudah menyatakan sebuah dokumen siap. Halaman ini menunjukkan cara memadukan keduanya.

Di mana work tinggal ​

Folder deuz/ ada di repository yang sama dengan kodenya, jadi work ikut di-commit seperti file lain. Untuk sekarang deuz mendukung satu repository. Spec dan kode berada di tempat yang sama.

Pola yang disarankan ​

Fase perencanaan: satu branch dokumen ​

  1. Analyst membuat branch untuk work, misalnya docs/pemesanan-buku.
  2. proposal.md dan specs/ ditulis di branch itu, lalu dibuka pull request khusus dokumen.
  3. Review dilakukan di PR, dengan komentar per baris. Persetujuan bisnis dicatat analyst setelah rapat.
  4. Setelah pemilik mengonfirmasi (/deuz:ready), file .deuz.yaml ikut berubah. Commit perubahan itu bersama dokumennya.

Designer dan backend/frontend bisa melanjutkan di branch yang sama, atau membuka PR dokumen sendiri untuk ui-design dan api-contract setelah PR sebelumnya di-merge.

Fase implementasi: branch per peran ​

Setelah api-contract disepakati, backend, frontend, dan QA bekerja paralel, masing-masing di branch kodenya sendiri. Setiap PR kode:

  • menyertakan perubahan tasks-<peran>.md (task yang dicentang);
  • menyertakan promote yang menjadi tugas peran itu, misalnya kontrak yang diterjemahkan ke file OpenAPI di PR backend, atau file desain yang disalin ke home desain di PR frontend. Konten masuk ke home bersama kode yang mengimplementasikannya.

Penutup: archive ​

Setelah semua PR di-merge, satu PR kecil berisi hasil /deuz:archive: delta yang digabung ke deuz/specs/ dan work yang dipindah ke work/archive/.

Review dan konfirmasi ​

TempatnyaYang dicatat
Review isiPull request dan diskusiKomentar, usulan perubahan
Konfirmasi "siap"/deuz:ready → .deuz.yamlPeran yang menyatakan siap, dan hash isi saat itu

deuz sengaja tidak memodelkan reviewer. Review sudah ditangani PR, dan menambahkan status review di deuz hanya menambah birokrasi.

Konflik di .deuz.yaml ​

.deuz.yaml adalah file teks biasa, jadi bisa bentrok kalau dua branch mengonfirmasi artifact berbeda di waktu yang sama. Cara mengatasinya:

  1. Selesaikan konflik dengan mengambil salah satu versi.
  2. Jalankan deuz status --write. deuz menghitung ulang status dari isi file dan menulis ulang .deuz.yaml tanpa mengubah konfirmasi yang tercatat.
  3. Kalau ada konfirmasi yang hilang karena konflik, pemiliknya cukup menjalankan /deuz:ready lagi.

Dari solo ke tim ​

Work yang dimulai satu orang (yang mengonfirmasi semua peran sekaligus) bisa diserahkan ke tim tanpa konversi:

  • Konfirmasi yang sudah ada tetap berlaku.
  • Kalau anggota tim mengubah dokumen, hash membuatnya kembali draft, dan pemilik perannya yang mengonfirmasi ulang.
  • /deuz:status menunjukkan siapa yang sedang ditunggu, memakai nama peran dari config.yaml.
