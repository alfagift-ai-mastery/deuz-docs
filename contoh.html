Empat contoh di aplikasi perpustakaan fiktif, dari awal sampai akhir. Setiap contoh menunjukkan perintah yang dijalankan dan potongan isi dokumen yang penting. Contoh lengkap per dokumen ada di panduan artifact.

1. Fitur baru dengan persetujuan bisnis ​

Kebutuhan: anggota ingin memesan buku yang sedang dipinjam orang lain, lalu mendapat giliran saat buku kembali.

Proposal (/deuz:new pemesanan-buku, lalu /deuz:continue proposal). Bagian yang paling menentukan:

markdown
| Type | feature |
|---|---|

## Ringkasan
Anggota bisa memesan buku yang sedang dipinjam dan mendapat giliran saat buku kembali, tanpa harus menanyakan
ke petugas setiap hari.

## Aturan yang perlu persetujuan bisnis
<!-- deuz:approval-rules -->
- `pemesanan-buku` → Requirement: Batas pesanan per anggota

## Capabilities
### Capability baru
- `pemesanan-buku`: anggota memesan buku yang sedang dipinjam dan dilayani sesuai urutan pesanan

## Area terdampak
- [x] design
- [x] frontend
- [x] backend
- [x] api
- [x] business
- [x] business-rules

Gate 1. Proposal dipresentasikan di rapat. Analyst mencatat keputusan dan persetujuannya, lalu:

/deuz:ready proposal --as analyst
/deuz:ready proposal --as business

Specs (/deuz:continue specs). Analyst menulis requirement, termasuk aturan yang ditunjuk proposal:

markdown
### Requirement: Batas pesanan per anggota
Sistem SHALL menolak pesanan baru bila anggota sudah memiliki 3 pesanan aktif.

#### Scenario: Pesanan keempat
- **GIVEN** anggota memiliki 3 pesanan aktif
- **WHEN** ia memesan buku lain
- **THEN** pesanan ditolak dengan pesan bahwa batas 3 pesanan sudah tercapai

Gate 2. Stakeholder menyetujui aturan batas pesanan. Analyst menambah baris Gate 2 di tabel Persetujuan, lalu:

/deuz:ready specs --as analyst,business

Desain, kontrak, task. Designer menulis ui-design (tombol Pesan, daftar antrean, pesan batas tercapai). Backend dan frontend menyepakati api-contract (misalnya POST /reservations, error limit_reached). Lalu ketiga daftar task ditulis dan dikerjakan paralel dengan /deuz:apply.

Archive. /deuz:archive membuat deuz/specs/pemesanan-buku/spec.md dan memindahkan work ke archive.

2. Bug fix tanpa dampak bisnis (jalur engineer) ​

Kebutuhan: tombol Pesan tetap nonaktif setelah halaman di-refresh, padahal spec menyatakan tombol aktif bila buku sedang dipinjam.

Engineer mendiskusikannya singkat dengan analyst. Kesimpulannya: perilakunya tidak berubah, hanya kode yang salah.

markdown
# Proposal: Tombol pesan setelah refresh

| Type | bug |
|---|---|

## Kenapa
Setelah refresh, tombol Pesan nonaktif walau buku sedang dipinjam. Spec `pemesanan-buku` menyatakan tombol aktif.

## Yang berubah
- Tombol Pesan kembali aktif setelah refresh bila buku sedang dipinjam.

## Scope
**Tidak masuk:** perubahan aturan pemesanan.

---
## Capabilities

## Area terdampak
- [ ] design
- [x] frontend
- [ ] backend
- [ ] api
- [ ] business
- [ ] business-rules

Triage: tidak ada dampak bisnis, dibahas dengan analyst pada 2026-11-12

Hasilnya setelah /deuz:ready proposal --as analyst:

  • specs di-skip (tidak ada capability, tidak ada delta);
  • ui-design, api-contract, dan tasks-backend di-skip (areanya tidak dicentang);
  • tinggal tasks-frontend dan tasks-test. Test regresinya masuk ke tasks-test.

3. Mengubah perilaku yang sudah ada ​

Kebutuhan: batas pesanan dinaikkan dari 3 menjadi 5. Ini aturan bisnis, jadi lewat jalur analyst.

Proposal mencantumkan capability yang diubah:

markdown
### Capability yang diubah
- `pemesanan-buku`: batas pesanan per anggota naik dari 3 menjadi 5

Delta spec-nya memakai MODIFIED dan menyalin blok requirement lama secara utuh:

markdown
## MODIFIED Requirements

### Requirement: Batas pesanan per anggota
Sistem SHALL menolak pesanan baru bila anggota sudah memiliki 5 pesanan aktif.

#### Scenario: Pesanan keenam
- **GIVEN** anggota memiliki 5 pesanan aktif
- **WHEN** ia memesan buku lain
- **THEN** pesanan ditolak dengan pesan bahwa batas 5 pesanan sudah tercapai

Kalau layar dan API tidak berubah, proposal hanya mencentang backend, frontend (kalau angka batas ditampilkan), business, dan business-rules. Saat archive, blok lama di spec permanen diganti blok baru.

4. Mulai di sistem yang sudah berjalan ​

Situasi: aplikasi sudah berjalan dua tahun, deuz/specs/ masih kosong, dan tim ingin mengubah aturan denda keterlambatan yang belum pernah ditulis.

  1. /deuz:init, dengan homes diarahkan ke folder desain dan file OpenAPI yang sudah ada.
  2. /deuz:baseline denda. Agent membaca kode perhitungan denda dan test-nya, lalu menulis deuz/specs/denda/spec.md untuk perilaku hari ini, lengkap dengan tabel contoh yang dihitung dari kode. Perilaku yang terlihat seperti bug masuk ke laporan sebagai temuan, bukan ke spec.
  3. Analyst membaca laporan itu dan menjawab pertanyaan yang diajukan.
  4. /deuz:new ubah-denda. Delta-nya memakai MODIFIED terhadap spec hasil baseline.

Area lain tidak perlu di-baseline sekarang. Spec-nya akan tumbuh saat area itu disentuh. Lihat Proyek yang sudah berjalan.
